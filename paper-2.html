Abstract

Code clones are common in software systems and often lead to maintenance and bug-related issues. Extract Method is a standard refactoring technique to remove duplication, but applying it correctly requires preserving behavior, compiling successfully, and satisfying structural constraints. Recent studies show that single-prompt Large Language Models (LLMs) can generate syntactically correct refactorings, yet they frequently produce incomplete or structurally invalid transformations, especially for Type-2 and Type-3 clones.

In this paper, we present a LLM-driven workflow for clone refactoring. The workflow decomposes the task into structured stages, including clone detection, refactoring generation, structural usefulness checking, compilation validation, and test-based behavioral verification. Across the detection, refactoring, and usefulness-checking stages, we employ multiple LLM-based agents to evaluate candidate outputs before proceeding to the next stage. We also incorporate retrieval-augmented generation (RAG) to guide the agents with curated Extract Method examples, while a PSI-based usefulness checker further enforces structural correctness beyond compilation and testing.

We evaluate the workflow on real-world clone instances collected from the ArgoUML project using Deckard. Results show that the workflow achieves 93.1% detection, 90.0% usefulness, 80.0% compilation success, and 69.2% test success overall on real-world clones. The results also show that clone size has a noticeable impact on refactoring stability. Medium-sized clones generally achieve the best balance between extraction context and structural manageability, while large clones remain more challenging due to increased dependency interactions and structural complexity.

Our ablation study further shows that retrieval-augmented generation (RAG) plays an important role in improving behavioral stability during refactoring. Removing RAG causes the largest decrease in overall test success, reducing the success rate from 70.0% to 30.8%. In contrast, removing the usefulness checker, feedback loop, or collaborative panelist architecture leads to smaller but still noticeable reductions in structural correctness and overall workflow reliability.

Our findings suggest that reliable LLM-based refactoring requires structured decomposition, explicit structural validation, and iterative feedback, rather than relying on one-shot code generation.

Workflow Prompts

Detection prompts

The detection stage uses three independent panelists followed by a curator. The panelists receive the same file and pasted snippet independently; the curator reviews their parsed outputs and produces the final clone detection result by majority vote.

Placeholders such as <FILE_SOURCE> and <SELECTED_SNIPPET> are filled at runtime. If the pasted snippet line range cannot be grounded, the implementation asks the model to locate the snippet occurrence in the file itself. Few-shot examples are included for panelists only when retrieval from the clone database succeeds.

You MUST focus on the pasted snippet and enumerate all other code regions in the file that are clones of it.
Do NOT report clones that do not involve the pasted snippet.
Ignore only truly trivial single-line repetitions.
Do not reject short, method-level, symmetric, or small-substitution clones merely because only a few identifiers, literals, casts, or method names differ.

Refactoring prompts

The refactoring stage uses three independent Java refactoring panelists. Each panelist receives the same Extract Method prompt and returns a structured refactoring plan. A curator then classifies the panelist candidates using usefulness categories and selects the best candidate for downstream validation.

Placeholders such as <FILE_SOURCE>, <CLONE_ID>, <TARGET_OCCURRENCES>, and <RAG_EXAMPLES> are filled at runtime. RAG guidance is included only when retrieved examples are available.

Refactoring panelist prompt template 
<PANELIST_TITLE> (<PANELIST_ID>)
You are one of three independent Java refactoring panelists.
Produce your own best Extract Method candidate for the provided target clone.
Do not try to match the other panelists. Return the strongest valid candidate you can.

You are an expert Java refactoring agent.
You specialize in clone removal via Extract Method and improving software quality (readability, maintainability, cohesion, and low coupling).
Follow the constraints and output format EXACTLY.
Do not skip the refactoring task. If the target clone can be extracted with parameters, you must still perform Extract Method.
If anything is unclear, prefer the most conservative valid Extract Method that targets the provided clone rather than leaving the file unchanged.

How to compile ArgoUML

How to compile ArgoUML (IntelliJ IDEA)

  1. Download and open ArgoUML

    Extract the ArgoUML source package and open the project folder in IntelliJ IDEA.

  2. Install Java 8 (Temurin)

    ArgoUML is compatible with Java 8. Download and install Java 8 from Adoptium if it is not already installed.

  3. Set the project SDK and language level

    Go to File → Project Structure and configure:

    • Project Settings → Project: set Project SDK to your installed Java 8 SDK and Project language level to 8.
    • Project Settings → Modules → Dependencies: ensure each module uses the Project SDK.
  4. Mark source directories

    In the Project view, right click the main source folders (for example src and resources) and choose Mark Directory as → Sources Root if needed.

  5. Add required libraries

    If ArgoUML includes a lib folder, add the JAR files from that folder as libraries in IntelliJ:

    • Add each required JAR via File → Project Structure → Libraries → + → Java.
    • Alternatively, use Maven or Gradle dependencies if the project includes a build descriptor.
  6. Build the project

    Run Build → Build Project in IntelliJ to compile ArgoUML. Fix any missing dependency warnings by adding the referenced JARs or updating the module configuration.
